# MVP Definition

## Decision

### First User Persona
`Tech lead`

The control pane should launch with the tech lead as the primary operator because that user feels the sharpest pain across delegation, code quality, risk management, and human approval. A tech lead already coordinates engineers and reviews work across repositories, so a control pane adds leverage without requiring the organization to trust full autonomy on day one.

### Highest-Value Workflow
`Delegate a scoped engineering ticket to an AI agent, inspect the evidence-rich execution trail, and approve or redirect the work before merge.`

This workflow is the best MVP anchor because it:
- fits the product promise of observability, control, and orchestration
- creates immediate value for both the tech lead and the implementing engineer
- can be measured with clear outcomes such as acceptance rate, cycle time, and review effort
- avoids the complexity and risk of production incidents or fully autonomous deployment flows

## Target User Story
As a tech lead, I want to hand a well-scoped ticket to an AI agent, monitor its progress across coding and testing steps, and approve or redirect the result with enough evidence to trust the outcome.

## MVP Workflow Narrative
1. A tech lead opens the control pane and selects a ticket from the intake queue.
2. They attach the repository, branch strategy, acceptance criteria, and relevant docs.
3. The pane launches an implementation agent with the team policy pack and repo memory.
4. The agent plans, edits code, runs allowed checks, and reports progress in real time.
5. The pane collects the diff, command trace, test evidence, and a concise rationale.
6. The tech lead reviews the package and chooses one of four actions: approve, request retry, re-scope, or escalate to a human engineer.
7. Once approved, the result moves into the normal merge flow with an audit trail.

## Core Jobs To Be Done
- Start an AI job with the right scope and constraints.
- See what the agent is doing without reading raw terminal output all day.
- Understand what changed and why.
- Decide whether the work is safe enough to merge.
- Capture feedback so the next run gets better.

## MVP Capability Slice

### Must Have
- Task intake for a ticket or scoped prompt
- Repository and branch selection
- Policy-aware agent launch
- Live run status with logs and milestones
- Diff and evidence review
- Human approval gate before merge
- Outcome capture for accepted, rejected, blocked, and retried runs

### Nice To Have
- Alternative implementation comparison
- Lightweight cost budget warnings
- Suggested retry actions based on prior failures

### Explicitly Out Of Scope
- Autonomous production changes
- Open-ended research agents with broad tool access
- Portfolio analytics for managers
- Deep workflow automation across multiple departments

## Success Criteria
- A tech lead can launch a scoped task in under 3 minutes.
- A reviewer can understand what the agent did from one task detail page.
- At least one meaningful action is available at every blocked state.
- The first merge-ready result contains enough evidence that the reviewer does not need to reconstruct the whole run manually.

## MVP Data Objects
- `Task`: the requested unit of work, scoped by repo, prompt, acceptance criteria, and risk level.
- `AgentRun`: a specific execution attempt with status, timing, logs, and cost.
- `EvidencePack`: the diff, commands, test results, and rationale generated by the run.
- `ApprovalDecision`: approve, retry, re-scope, or escalate, with notes.
- `PolicyPack`: the applicable permissions, budgets, and restrictions for the run.

## Default MVP Scenario
The ideal first demo is a tech lead delegating a medium-complexity backlog item such as a UI enhancement or API improvement, watching the agent move through implementation and tests, then reviewing an evidence-backed diff before approving a pull request.
